## Goal

Replace credit RPCs that trust caller-supplied transaction fields with a two-stage design: a trusted verifier persists immutable, chain-derived evidence; a narrowly scoped credit RPC consumes one evidence record atomically. This document does not implement the verifier or alter database privileges.

## Proposed trusted evidence record

A future schema should record, at minimum:
- Unique evidence ID generated by the database.
- Network/chain identifier and asset symbol.
- Canonical transaction hash and exact output index or event/log index.
- Canonical block number/hash and transaction inclusion state.
- Successful transaction receipt where the chain supports receipts.
- Exact destination address, normalized using chain-specific rules.
- Exact native amount in integer base units; for tokens, contract address and token amount in integer base units.
- Required confirmation policy/version and independently observed confirmation count.
- Verifier identity/version, observation timestamp, and a status such as `verified`, `orphaned`, or `rejected`.
- Consumption/credit state, unique credited ledger/deposit reference, and audit timestamps.

Amounts must not be accepted from a webhook body or arbitrary RPC caller as authoritative. Preserve exact integer base units through verification and convert to display decimals only at the application boundary.

## Verifier trust boundary

- Only a server-side verifier using configured, trusted RPC/provider access may create or advance evidence.
- Browser clients, `anon`, and `authenticated` roles must not insert or update evidence.
- Webhook providers may trigger a recheck, but a webhook payload alone is never evidence and must not directly create a creditable record.
- EVM verification must bind chain ID, tx hash, successful receipt, canonical block hash, exact token contract, event signature, recipient, and amount/log index.
- UTXO verification must bind txid, exact vout, script/address, asset amount, canonical inclusion and confirmation depth.
- TRON verification must bind the correct network, successful execution, exact TRC-20 contract/event or native transfer, recipient and amount.
- Reorg monitoring must invalidate unconsumed evidence when inclusion ceases to be canonical. Define a separate, audited compensating policy for already-credited reorgs; do not silently rewrite ledger history.

## Credit RPC contract

The new credit function should accept only an evidence UUID, not user ID, amount, asset, address, confirmations, tx hash or output index from the caller.

Within one database transaction it should:
1. Lock the evidence row.
2. Require `verified` status, not previously consumed, and policy threshold satisfied.
3. Re-derive recipient ownership from the authoritative deposit-address registry and validate the matching wallet/account is eligible.
4. Enforce unique event identity on network + canonical tx hash + output/log index (plus asset/contract where the schema requires it).
5. Create deposit, on-chain record and balanced ledger entries from the stored evidence values.
6. Update the appropriate wallet balance using existing canonical locking/ledger rules.
7. Mark the evidence consumed and store the resulting deposit/ledger identifiers.
8. Return an idempotent already-processed result for an identical retry; reject any mismatch.

Only the verifier/credit service role should be able to invoke the relevant routines. SECURITY DEFINER functions must use a fixed safe search_path, fully qualify objects, and have explicit grants. Do not grant the evidence-write path to `service_role` broadly if multiple app components share that role; isolate it behind the trusted verifier boundary where possible.

## Required tests before any cutover

- forged confirmations cannot create evidence or credit.
- mismatched destination/user, chain ID, asset, token contract or amount is rejected.
- failed EVM receipt / failed transaction is rejected.
- same tx with different log/output indices is handled correctly; duplicate same event credits exactly once.
- concurrent duplicate credit requests yield one ledger credit.
- webhook replay cannot alter evidence or amount.
- noncanonical/reorged blocks invalidate evidence before credit.
- caller cannot choose the evidence's owner or modify a verified row.
- zero, negative, over-precision, overflow and malformed amounts are rejected.
- credit failure rolls back deposit, balance, ledger and evidence-consumption state together.
- RLS/ACL tests prove `anon` and `authenticated` cannot write evidence or execute privileged credit routines.

## Cutover gates

Do not re-enable deposit providers until all are true:
1. Full repository caller map is completed with local whole-tree searches and SQL dependency/trigger inspection.
2. The verifier is implemented and independently tested on supported networks.
3. The new credit RPC is tested against a staging database with synthetic fixtures, including concurrency and replay.
4. Every caller is migrated and production/external scheduler ownership is known.
5. Legacy credit functions are revoked/retired in a reviewed migration only after dependencies are proven safe.
6. Runtime tests, full suite, typecheck, lint and production build pass.
7. Operators have documented pause/resume, reconciliation, reorg, alerting and incident procedures.

## Scope and safety

This is a design artifact, not proof that the system is production-ready. No database objects, grants, financial rows, environment variables, merge or deployment were changed. Deposits remain paused on this draft branch.
